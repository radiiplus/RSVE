# RSVE Dependency Architecture Review

Review date: 2026-11-19. Sources are primary project documentation or project repositories. The repository declares one runtime dependency, `z3-solver==4.12.6.0`, and records it in `requirements.lock`. Foundry and QEMU remain external, capability-gated tools rather than Python package dependencies.

## Decision summary

Adopt now: **`z3-solver==4.12.6.0` for the solver boundary, Foundry v1.9.0 for the controlled EVM fixture, and system QEMU 8.2.2 plus `qemu-img` for the Linux substrate fixture**. Python core and Node work use standard-library/runtime APIs. Foundry and QEMU are external tools, not Python dependencies; their installed versions and the pinned Ubuntu image are recorded here for replay reproducibility.

| Capability | Candidates and evidence | License / health / platform | API fit, cost, gaps | Decision and adapter boundary |
| --- | --- | --- | --- | --- |
| SMT solving | Z3; cvc5; both expose APIs and SMT-LIB boundaries. Z3 documents Python and other bindings; cvc5 documents Python/Java APIs and SMT use. | Z3 MIT, active releases and broad OS support. cvc5 modified BSD, active releases, but optional GPL-linked configurations must be controlled. | Z3 is the smaller Python integration and is present as `z3-solver 4.12.6.0`; both are native solver runtimes with nontrivial proof/model/core semantics and platform packaging. Neither solves target-fidelity problems. | **Adopt Z3 `4.12.6.0` through `Z3SolverAdapter`; keep cvc5 optional.** SMT-LIB-like query text is retained, unsupported theories return UNKNOWN, cores are distinct from proofs, and no fork is needed. |
| Generic source parsing | Python `ast`; Tree-sitter. Tree-sitter is incremental, error-tolerant, multi-language, and has official Python/Node bindings. | `ast` is Python stdlib. Tree-sitter core is MIT; language grammars have their own licenses and must be checked individually. | `ast` fits Python fixtures at zero footprint. Tree-sitter handles multi-language syntax but parses source; neither observes runtime behavior. | **Use stdlib `ast` for Python fixtures; defer Tree-sitter.** If multi-language declared-surface discovery becomes required, wrap Tree-sitter behind a parser adapter; do not make it the runtime observer. |
| Trace/export conventions | RSVE `TraceEvent`; OpenTelemetry/OTLP. OTel tracing has stable span/event/context conventions and broad exporters. | OTel project uses permissive open-source components; exact language SDK versions/license notices must be pinned when adopted. Specification is actively versioned. | OTel spans are observability records, not complete state checkpoints, symbolic constraints, snapshots, or proof artifacts. Adding an SDK now would create a second schema and runtime dependency. | **Keep RSVE canonical schema.** Add a thin OTel/OTLP mapping adapter later, retaining RSVE-specific fields and loss metadata. |
| Node instrumentation | Node built-in `node:inspector`; `node:diagnostics_channel`; stable `node:async_hooks`/`AsyncLocalStorage`; optional OpenTelemetry Node SDK later. | Node is an external runtime, not a Python package dependency. Current environment has v24.21.0; project support range is unresolved. Built-ins follow Node release/support policy. | Inspector exposes Chrome DevTools Protocol integration; diagnostics channels and async context are opt-in and target/framework-dependent. They do not automatically observe all transforms or lower layers. | **Use diagnostics channels plus AsyncLocalStorage for the fixture in `src/rsve/node_adapter.py`; keep Inspector as a future narrowly-scoped hook.** Treat missing events as unsupported/unknown, never safe. No third-party instrumentation package now. |
| Persistent evidence storage | Python `sqlite3`; external database/ORM; current JSONL store. | SQLite core is public domain, stable, embedded, and already available as Python stdlib; current library is 3.45.1. External DBs add services and dependencies. | SQLite supplies transactions, indexes, and a durable single-file artifact ledger. It does not define RSVE schema or secret policy. JSONL is useful for small append-only fixtures but lacks atomic indexing/query semantics. | **Adopt stdlib `sqlite3` through `SqliteArtifactStore`; retain JSONL as export/debug format. No ORM, server, or bespoke graph database.** |
| Deterministic replay | rr; CRIU/Docker checkpoint; explicit adapter snapshot/reset. | rr is active and GPL-licensed, Linux/kernel/CPU constrained. CRIU checkpoints/restores processes but depends on kernel features and host compatibility; Docker checkpoint is experimental and requires CRIU. | rr is concrete record/replay, not symbolic/concolic analysis and not portable across RSVE targets. CRIU is process-state replay, not a semantic target snapshot. Both have significant host prerequisites. | **Defer and wrap only on evidence.** First define RSVE snapshot/reset semantics and environment adapter. No install. A future Linux replay adapter must report host/kernel/CPU constraints. |
| Native dynamic observation | DynamoRIO; Frida. | DynamoRIO is primarily BSD, with LGPL extensions. Frida core uses wxWindows Library Licence 3.1 and has active releases. Both are native, platform-specific toolchains. | They observe/instrument native execution; they are not source parsers, generic runtime adapters, or objective planners. Frida is broader for injection; DynamoRIO is stronger for controlled instruction-level tooling. | **Defer.** Choose one only for a measured native target. Wrap public APIs; do not fork. Keep instrumentation evidence separate from symbolic execution. |
| Native symbolic/concolic analysis | angr; Triton; KLEE. | angr is BSD and Python-oriented but has a large native/analysis dependency graph. Triton is a C++/Python dynamic binary/concolic library; exact transitive licensing requires a target-specific review. KLEE is UIUC-licensed and depends on LLVM plus solver infrastructure. | angr is a binary-analysis platform, Triton is dynamic binary analysis/concolic execution, KLEE is LLVM-based symbolic execution. None is a runtime-neutral target adapter; all introduce substantial build/coverage constraints. | **Reject for current batches; roadmap only.** Select per target evidence and wrap as an optional backend. No fork/vendor decision is justified. |
| Whole-system substrate | QEMU 8.2.2; S2E. | QEMU is primarily GPLv2 with component-specific licenses. S2E is a VM/selective-symbolic platform with substantial QEMU/KLEE/LLVM substrate needs. | QEMU provides a portable x86_64 machine boundary, serial evidence, and qcow2 overlays; TCG is slower than KVM and does not make guest behavior globally deterministic. S2E remains a much larger selective-symbolic stack. | **Adopt installed QEMU 8.2.2 through `QemuLinuxSubstrate`; use TCG, an official Ubuntu Server 26.04 cloud image, and recreated qcow2 overlays. Defer guest agents and S2E.** |
| JVM adapter roadmap | `java.lang.instrument`; Byte Buddy; ASM. | `java.lang.instrument` is part of the JDK. Byte Buddy is permissively usable; ASM has its own BSD-like license and notices. | The JDK agent API is the smallest stable observation boundary. Byte Buddy can reduce bytecode manipulation work; ASM is lower-level. Neither is needed for Python/Node batches. | **Roadmap option:** start with JDK instrumentation, add Byte Buddy only when measured transformation complexity warrants it. No dependency now. |
| EVM adapter | Foundry/Anvil v1.9.0; Slither. | Foundry declares MIT OR Apache-2.0 for its crates. Slither is AGPLv3. | Anvil is the controlled EVM runtime/replay substrate; Forge builds the fixture and Cast performs ABI encoding. Slither remains source-analysis tooling and is not installed. | **Adopt Anvil/Forge/Cast v1.9.0** through `src/rsve/evm_adapter.py`; use only for the local fixture. Keep Slither deferred. |

## Candidate classification

- **Adopt through stable adapter:** Python stdlib `ast`, Python stdlib `sqlite3`, Node built-in Inspector/diagnostics APIs, and QEMU's CLI/image tooling through `QemuLinuxSubstrate`.
- **Wrap an existing CLI/library later:** cvc5, rr/CRIU, S2E, angr/Triton/KLEE/DynamoRIO/Frida.
- **Extend through a supported API:** OpenTelemetry/OTLP mapping; JDK instrumentation; Byte Buddy if needed.
- **Fork/vendor:** none justified by repository evidence.
- **Reject for now:** overlapping parser/observer stacks, ORM/database servers, a universal binary/runtime framework, and any dependency added only because it is popular.
